# Exchange EDI documents reliably

An EDI exchange has three separate conversations stacked on each other: did the bytes arrive, is the document well formed and valid, and does the business accept it. Standards keep them apart, and most intake defects come from collapsing them: treating a transport receipt as acceptance, rejecting a document for a warning, or processing the same file twice because the file name was the only key. Decide for each level what you check, what you store, and what you answer.

This skill covers the pipeline around a document. For the meaning of the fields inside an order or invoice, see a document-mapping guide; for the codes and identifiers in them, see a codes-and-identifiers guide.

## Keep the three acknowledgement levels apart

| Level | What it says | Examples | What it does not say |
| --- | --- | --- | --- |
| Transport receipt | The bytes arrived intact from an identified sender | AS2 signed MDN, AS4 `eb:Receipt`, "file picked up" | That the document parses, validates or will be processed. AS4 states normatively that no delivery semantics can be assumed from a receipt; RFC 4130's own example says the receipt is not a guarantee the message was processed or understood |
| Syntax or validation response | The document is or is not structurally and semantically valid | EDIFACT CONTRL, Peppol Message Level Response (being phased out in favour of Message Level Status; check the current status) | A business decision. GS1's EANCOM text: CONTRL reports on the syntax level, not the business content |
| Business response | The receiving application accepts, rejects or queries the document | EDIFACT APERAK, Peppol Invoice Response, an ORDRSP answering an ORDERS | Anything about transport |

Rules that follow from the specifications:

- Return the transport receipt even when processing fails. RFC 4130 requires a signed MDN when one was requested, including on processing errors.
- Send a syntax-level response only when the partner agreement asks for it. EANCOM: generate CONTRL only when the partner supports it, one CONTRL per interchange, as a separate interchange, and never a CONTRL in reply to a CONTRL. Peppol: when a Message Level Response was requested, answer accepted, rejected or acknowledged; when not requested, send only a rejection, and never a status message in reply to a status message.
- The business response comes from the application, not the translator. EANCOM states that APERAK should be generated by the application software, that it must not be used to acknowledge receipt of an interchange, and that one APERAK answers exactly one message. Where a dedicated answer exists (an ORDRSP for an ORDERS, an Invoice Response for an invoice), use it instead of a generic acknowledgement.
- Expect application-level rejections to need a person. The APERAK specification itself says application errors will often need manual processing.

## Validate in stages and reject only on fatal errors

Peppol describes validation as stages with shifting focus: well-formedness and schema, then the semantic rules (code lists, mandatory terms, calculations), then the profile's own rules, then country rules. EDIFACT has the equivalent envelope stage first: the interchange trailer must repeat the header's control reference and the count of messages (or of functional groups, when groups are used), and each message trailer must repeat the message reference and the segment count. An interchange trailer mismatch rejects the interchange; a message trailer mismatch rejects that message.

Within those stages, every rule is either fatal or a warning. Peppol's compliance text: a message is compliant if no fatal errors are detected, a receiver may reject a non-compliant message and shall not reject a compliant one, and warnings alone cannot cause a rejection. EANCOM allows accepting non-fatal syntax errors such as an element that exceeds its maximum length. Build the validator the same way: a list of findings with a severity each, and a rejection decision taken on the fatal ones only. Log the warnings, and report them with the rejection if there is one, but do not turn them into one.

Validate outbound documents against the same rules before sending. Peppol puts it as an obligation: a sender shall not send a non-compliant message.

## Make intake idempotent on the document's own identity

Duplicates arrive. The AS4 profile requires the receiver to detect or eliminate them, and if it only detects, to notify the application. Hohpe and Woolf's Idempotent Receiver names the two choices: track what you have seen, or make processing repeat-safe. Do both where you can.

Choose the key from the document, not from the transport:

- EDIFACT: the interchange sender plus the interchange control reference, which the syntax guidelines describe as the unique reference for the transmission allocated by the sender; the message reference number within the interchange for per-message tracking.
- AS4: the message id. The profile says duplicate detection relies only on it, and a resent message must keep the same id.
- Peppol UBL: the envelope instance identifier, which the Message Level Response references.
- A file drop with no envelope: the file name is a weak key. Camel's default idempotent key is the absolute path with name plus size as the suggested alternative; Spring keys on name plus remote modification time. Prefer a document identifier from inside the file, always paired with the sender, because one provider can carry documents from several partners who allocate the same numbers; keep the file-level key as a second check.

Keep the seen-keys store persistent and shared across instances; both Camel and Spring warn that an in-memory store is only for a single process that never restarts. Decide how long keys are kept; AS4 leaves the window to the implementation, so write yours down.

On the sending side, persist the outbound document and its id before the first send attempt, so that a retry reuses the id and the partner can deduplicate. Hohpe and Woolf's Guaranteed Delivery is the same rule for internal queues.

## Keep the raw document and the envelope

Store the file exactly as received, with the transport metadata (sender, received time, control or message reference, file name). Reasons from the specifications: precise CONTRL error reporting requires access to the interchange in the form it was transferred; a CONTRL copies the original message header data verbatim; non-repudiation of receipt under AS2 is only possible by comparing the original's integrity check with the signed receipt. Hohpe and Woolf's Message Store is the general pattern: a copy of each message, or at least its id, channel and timestamp, for audit and reporting.

Keep a per-document trace of what happened at each level (received, validated with findings, acknowledged, handed to the application, answered). Correlate replies to the original by the original's id, as every acknowledgement format above does.

## Pick up files without racing the writer

A file on an SFTP server can be visible before the upload has finished. Camel notes that the standard file API cannot always tell whether another process is still writing. Camel, Spring Integration and Azure's connector recommend the same order of preference:

1. Agree with the writer that they upload under a temporary name and rename when complete, or write a marker file after the data file. Camel recommends that writers write elsewhere and move into the drop folder; Spring's own adapter writes its local copies under a `.writing` suffix and renames them on completion, the same practice asked of the partner; Azure's connector waits until a file's timestamp is unchanged across two polls.
2. If the writer cannot do that, poll twice and act only when size and modification time are unchanged, or ignore files younger than a minimum age.

Then run intake in this order: record the key as in progress, copy the file to the archive, parse and validate, hand the result to the application, and only then delete or move the original. Camel's `move`, `preMove` and `moveFailed` options are that sequence made explicit, with failed files moved aside so they are not picked up again. Process files in a deterministic order (modification time, then name) and keep the folder you poll separate from any folder you write to.

Spring's filter rolls back on an I/O error during transfer but not on a downstream failure; decide which failures release the key for a retry (transfer errors) and which park the document for a person (validation and application errors). Hohpe and Woolf call the two destinations the Invalid Message Channel, for input the receiver cannot make sense of, and the Dead Letter Channel, for messages that could not be delivered after retries. Keep them distinct, because a parse failure and a business rejection need different people.

## Report rejections so the sender can act

Separate "could not read it" from "read it, but it is wrong". The first produces a syntax-level response or a parking of the file with the parser's finding; the second produces a business response with a reason the sender can act on. Peppol's Invoice Response carries a status, a reason code and an action code, optionally naming the business term and the corrected value, and expects a first response within three working days; its successor to the Message Level Response makes location, description and reason code mandatory for a rejection. EANCOM asks for one CONTRL listing all errors as precisely as possible, not one per error.

When the original is so broken that a structured response cannot be built from it, report by another channel; EANCOM states this explicitly.

## Example: an order intake from a provider's SFTP drop

A provider drops `ORDERS_<n>.xml` files containing one or more order documents and requires each file to be deleted after use. An intake job following this skill:

1. Lists the folder, sorted by modification time then name, skipping files younger than one poll interval unless the provider renames on completion.
2. For each file, inserts `(provider, file_name, file_size, sha256)` into an `edi_intakes` table with status `in_progress`; a unique index on `(provider, sha256)` catches a file already seen. If the existing row is `completed`, the job logs the duplicate and deletes the file. If it is `in_progress`, the job tries to claim it with one atomic update that sets its own worker id and a fresh lease expiry only where the previous lease has expired; a claim that updates no row means another worker is still on it, and the job leaves the file alone. Only a successful claim resumes the intake.
3. Copies the bytes to object storage keyed by the intake id before parsing anything.
4. Parses the file. A parse failure sets status `unreadable`, keeps the file in a `failed/` folder on the server and opens an alert; nothing is deleted.
5. Validates each document and records findings with severity. Fatal findings mark that document `rejected` with its findings; warnings are stored and the document continues.
6. In one transaction, writes accepted documents into `orders` keyed by `(provider, sender, document_number)`, branching on the document's message function (an original or replacement updates the row, a duplicate changes nothing, a cancellation marks the order cancelled), and creates the business answer the agreement defines (an order response, or a rejection with reasons) as a row with its own id and status `pending`, linked to the intake row. A change to an order that the application has already accepted is recorded as a finding for a person, not applied.
7. Deletes the file from the server only after step 6 commits. From here on the pending answer row, not the file, is what a retry resumes from.
8. Sends the pending answer and records each attempt and its outcome on its row. A retry after a crash finds the pending row and resends the same answer with the same id.

Nothing in this sequence sends a transport receipt, because an SFTP drop has none; if the exchange later moves to AS2 or AS4, the receipt is added at step 1 and the message id becomes the intake key in step 2.

## Judge the result

- Re-run the intake over the same file twice. The second run must produce no new rows, no second business response, and a log line saying why.
- Drop a half-written file into the folder. It must be left alone until complete, not parsed as empty or truncated.
- Introduce a warning-level finding and a fatal one. Only the fatal one rejects, and the rejection names the location and reason.
- Delete the processed file by hand and ask for the original. If it cannot be produced from your archive, the raw document was not kept.
- Ask who gets paged for an unreadable file and who for a business rejection. If it is the same person for the same reason, the two channels have merged.

Leave an existing pipeline alone when it already keeps its keys, archives and responses apart; this skill is for new intakes and for pipelines that have produced a duplicate, lost a file, or answered the wrong level.
